# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Requires **Node 24+** (see `.nvmrc`). No build step: Node runs the `.ts` sources directly via type stripping, so only erasable TypeScript syntax is allowed (no `enum`, `namespace`, or constructor parameter properties; `tsconfig.json` sets `erasableSyntaxOnly`). Relative imports use the `.ts` extension.

```bash
npm test                                   # all suites (node:test)
node --test tests/checks.test.ts           # one file
node --test --test-name-pattern="hier-no-cycles" tests/checks.test.ts   # one test
npx tsc                                    # typecheck (noEmit)
node src/cli.ts <command>                  # run okb without npm link
npm run build:meta                         # compile meta-kb/src/*.yaml -> meta-kb/data/*.json
npm run docs                               # regenerate docs/METHOD|GLOSSARY|RULES|DECISIONS.md
npm run example                            # rebuild examples/wine/ (also run by npm test)
npm run format:docs                        # Prettier on the hand-written docs
npm run lint:docs                          # Prettier check + markdownlint + Vale (brew install vale; vale sync once)
```

Run `npx tsc` and `npm test` after every change. There's no code linter. `npm run lint:docs` fails on Vale errors (spelling, `e.g.`, wrong-case terms) and shows its warnings (passive voice, wordiness) as suggestions to weigh, not rules. Add project terms to `.vale/styles/config/vocabularies/Okb/accept.txt`; it's case-sensitive.

**Tests regenerate tracked files.** `tests/misc.test.ts` runs `meta-kb/build.ts` and `examples/build-wine.ts`, which rewrite `meta-kb/data/*.json` and everything in `examples/wine/`. A diff in `examples/wine/TRANSCRIPT.md` after a refactor means CLI output changed, so treat it as a behavior change and check it. `okb.json` records today's date, so it differs on a new day; that part is expected.

## Architecture

okb is a CLI that guides a beginner through the 8-step Ontology 101 method. It has two graphs, and both use the same labeled property graph (LPG) shape (`nodes.json` + `edges.json`):

1. **The meta-KB** (`meta-kb/`) holds the method, glossary, principles, decision guides, rules, and the file-format registry. It is authored as YAML in `meta-kb/src/`, compiled by `meta-kb/build.ts` into committed JSON in `meta-kb/data/`, and read at runtime by `src/metakb.ts` (`MetaKB.get()` singleton).
2. **A user's ontology**: a folder with `okb.json`, `nodes.json`, and `edges.json`, loaded by `Ontology` in `src/model.ts`. In this file the schema is data: classes, slots, and instances are all nodes.

### The meta-KB is the source of truth; the build enforces it

- Every mechanical or heuristic rule in `meta-kb/src/rules.yaml` must have exactly one check with the same key in `CHECKS` in `src/checks.ts`, and the reverse. `meta-kb/build.ts` fails if they drift apart. The `tests/checks.test.ts` suite fails if any key in `CHECKS` has no fixture that triggers it (via `fires()`).
- Each step's `doneWhen[].check` key in `steps.yaml` must exist in `STEP_CHECKS` in `src/status.ts`.
- A rule's severity comes from its modality (MUST → error, SHOULD → warning, MAY → info). An override needs a written `severityReason`. `fromStep` hides non-error findings until the user reaches that step.
- Adding or changing a rule: edit the YAML, add or adjust the check and its fixture, then run `npm run build:meta && npm run docs && npm test`. Bump `VERSION` in `meta-kb/build.ts` when a rule's meaning changes.
- `docs/METHOD.md`, `GLOSSARY.md`, `RULES.md` and `DECISIONS.md` are generated by `src/gendocs.ts`, so never edit them by hand. `docs/FORMAT.md` and `docs/EXTRACTION-PIPELINE.md` are hand-written.
- `meta-kb/src/format.yaml` is the registry of node and edge types that `struct-well-formed` validates against.

### Layers in `src/`

- `cli.ts` parses arguments and dispatches commands. `property` and `relationship` are rewritten to `slot` (and `--from`/`--to` to `--on`/`--range`) before dispatch. Most mutating commands go through `mutate()`: load → call an op → save → print notes.
- `ops/*.ts` (re-exported by `ops.ts`, split by reason to change: naming, scope, classes, slots, values, links, instances, admin) and `provenance.ts` hold every mutation. Each op takes an `Ontology`, changes it in place, and returns `Notes` (strings shown to the user, including teaching tips). Throw `OkbError` (`errors.ts`) for user-facing problems; the CLI prints it without a stack trace and exits with code 2.
- `model.ts` (`Ontology`) handles load and save (atomic `.tmp` + rename), the indexes, lookup (`find()` accepts ids, names, `class:Foo` prefixes, and bare numbers for questions and decisions), and hierarchy, slot, and facet queries. `nodes` and `edges` are read-only from outside: add through `addNode`/`addEdge` (which update the indexes in place) and remove through `removeEdges`/`removeNode` (which reindex).
- `types.ts` types the file format as a discriminated union, `OkbNode`, keyed on `type`. `ofType("Slot")` returns `SlotNode[]`, and `find(ref, "Class")` returns a `ClassNode`. For ids that must exist (edge ends, stored slot ids), use `ont.require(id, type)` rather than `get(id)!`: on a hand-edited file it throws a readable `OkbError`. Checks that validate hand-edited data narrow with `n.type === ...` instead of casting. `GraphNode` (untyped) remains only for tests of malformed input. The meta-KB has its own typed nodes (`MetaRule`, `MetaStep`, ...) in `metakb.ts`.
- `checks.ts` holds the validator. `runChecks()` returns `{ findings, hiddenLater }`: it attaches severity, hides (and counts) non-error findings from later steps, and marks warnings as `explainedBy` a `DesignDecision` that waives the rule. A decision about a class also covers its subclasses.
- `status.ts` tracks step progress. Its "no errors in this part" checks count the rules the meta-KB links to those steps (`meta.stepRules`), so which rules gate a step is data in `steps.yaml`, not code. `review.ts` turns judgment-only rules into questions (`okb review`, used by the ontology-review skill). `render.ts` holds terminal output. `export.ts` writes JSON and openCypher export.
- `markdown.ts` splits documentation markdown into quotable blocks with heading paths and line ranges. `quotes.ts` does normalized verbatim-quote matching for PDF and text.

### Relationship storage (the subtle part)

A slot with `valueType: "Instance"` is a **relationship**. Its values are stored as edges whose type is the slot's `relType` (the slot name in UPPER_SNAKE case: `maker` → `:MAKER`). They are not stored on the node. Inverse slots share one edge: the `from` side of `INVERSE_OF` is the stored direction, and the other slot reads the same edges backwards (`ont.rel.spec(slot).reverse`). An edge from a Class is a fixed class-level value inherited by its members.

`src/relationships.ts` is the one module that knows this, and it's reached as `ont.rel`. Read and write relationship values through `ont.rel.values`, `link`, `unlink` and `edge` (or `ont.statedValues`, which combines literal and relationship values), never by building edges directly. Schema changes go through its intents: `becomeRelationship`, `becomeProperty`, `declareInverse`, `rename` and `drop` (call `drop` before `removeNode` on a slot). Property values are stored on nodes instead (`Instance.values[slotId]`, `Class.fixedValues[slotId]`). `okb-lpg/1` files (`HAS_VALUE` edges) are migrated on load.

`docs/CODE-REVIEW.md` is a worklist of quality issues with a suggested order and a status for each item. When working through it, make each item its own commit, don't mix a refactor with a behavior change, and run `npx tsc` and `npm test` after every step.

## Skills in this repo

`skills/` contains SKILL.md files that ship with the toolkit: `ontology-coach`, `ontology-review`, and `build-domain-kb-from-docs`. They drive the `okb` CLI, so a change to command names, flags, or output that they rely on must be reflected there too.

`.claude/skills/okb-docs-drift` is a development skill (not shipped) that checks the hand-written docs and these skills against the CLI and meta-KB. After changing commands, flags, file layout or rules, run `node .claude/skills/okb-docs-drift/scripts/check-docs.ts`.
