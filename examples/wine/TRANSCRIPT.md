First a naming convention (the defaults), then classes. We work in the paper's 'combination' style: Wine at the top, the familiar color groups in the middle, and specific wines below.

```console

```

```console
$ okb class add Wines --parent Wine --force
✗ 'Wines' can't be a subclass of 'Wine': they're the singular and plural of the same concept, so neither is a kind of the other (Ontology 101 §4.1: "a single Wine is not a kind of Wines"). Use one class.
```

Even with --force, okb refuses 'Wines' as a subclass of 'Wine'. That's Ontology 101's classic singular/plural mistake (§4.1).

## Step 5: Slots

The paper calls every attribute a *slot*. There are two kinds: **properties** hold a value, and **relationships** link to another thing and are stored as graph edges (`maker` → `:MAKER`). Slots go on the most general class whose members all have them, so tanninLevel goes on RedWine, not Wine (§3, Step 6).

Now on step 6. (To read a step's guide without moving: okb explain 6)

Step 6 of 8: Define the facets of the slots

  Goal: For every slot, decide its value type, allowed values or range, cardinality, and any
  defaults, fixed values or inverse.
  Why it matters: Facets turn a list of fields into rules a machine can check. This is where
  most data-quality errors get caught later.

Questions to answer
  • Is the value text, a number, yes/no, one of a fixed list, or another thing (Instance)?
  • If it's a fixed list, what are all the allowed values?
  • If it's another thing, what is the most general class of things it can be (the range)? Not
  too general, not too narrow.
  • One value or many? Is it required (minimum 1)?
  • Is there a value most instances share (default), or one every instance of a class must have
  (fixed value)?
  • Is this relationship the reverse of another slot (maker ↔ produces)?
  • Does each link need extra information of its own, like a condition or a strength? (Edge
  properties; see decision.edge-or-class.)

You're done when
  ○ Every slot has a value type and cardinality
  ○ No errors in slot checks

Tips
  • When in doubt about range, pick the most general class that still only contains valid
  fillers.
  • Defaults are suggestions; fixed values are facts. Don't confuse them.

In the paper's wine example
  body: Enumerated {light, medium, full}, single. produces (on Winery): Instance, range Wine,
  multiple, inverse of maker. grape: min 1. Dessert Wine fixes sugar = sweet.

  decision.edge-or-class       Edge property, or make the relationship its own class?

## Step 6: Facets, fixed values, inverses

Fixed values are facts about a whole class. Every red wine's color is red, and every dessert wine is sweet (§5.2). A pairing stated on a class applies to all its members.

```console
$ okb relationship inverse maker produces
maker and produces are now inverses: one relationship read from both ends.
Stored as (Wine)-[:MAKER]->(Winery); produces follows MAKER backwards, so nothing is stored twice.
```

```console
$ okb class fix RedWine color=red
RedWine.color fixed to "red"
Fixed values apply to every subclass and instance and can't be changed below. For an overridable starting value use `okb class default`.
```

```console
$ okb class fix WhiteWine color=white
WhiteWine.color fixed to "white"
```

```console
$ okb class fix RoseWine color=rose
RoseWine.color fixed to "rose"
```

```console
$ okb class fix DessertWine sugar=sweet
DessertWine.sugar fixed to "sweet"
```

```console
$ okb class fix RedWine goesWellWith=RedMeat
RedWine.goesWellWith fixed to RedMeat
```

```console
$ okb class fix WhiteWine goesWellWith=Seafood
WhiteWine.goesWellWith fixed to Seafood
```

A pairing's strength belongs to the pairing itself, not to the wine or the food, so it's an **edge property** (see `okb explain decision.edge-or-class`).

```console
$ okb relationship property goesWellWith strength --type Enumerated --values classic,good
goesWellWith edges can now carry strength (Enumerated): (…)-[:GOES_WELL_WITH {strength: …}]->(…)
```

```console
$ okb link RedWine goesWellWith RedMeat strength=classic
Updated (RedWine)-[:GOES_WELL_WITH {strength: "classic"}]->(RedMeat)
```

## Export for a graph database

In the okb files, classes are nodes so the schema can be checked. A graph database usually wants the data the other way round: each instance becomes a node labeled with its class and all its ancestors, with properties (including fixed values inherited from classes) and typed relationships.

```console
$ okb export --format cypher --out wine.cypher
Wrote wine.cypher: 9 nodes, 5 relationships (cypher).
  2 class-level relationship value(s) point at classes (e.g. RedWine GOES_WELL_WITH RedMeat), not instances, so they're only exported with --with-schema.
  Inverse relationships are stored once: produces = MAKER followed backwards.
```

```console
$ okb export --with-schema --out wine-export.json
Wrote wine-export.json: 30 nodes, 37 relationships (json).
  Inverse relationships are stored once: produces = MAKER followed backwards.
```
